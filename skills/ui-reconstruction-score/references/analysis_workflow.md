# 分析工作流

## 标准化

在比较前对截图进行归一化处理：

1. 加载时应用 EXIF 方向。
2. 转换为 RGB。
3. 将两张图片缩放至相同逻辑宽度，不拉伸。
4. 忽略顶部状态栏/系统信息区域。归一化后默认为 44 逻辑像素，除非项目配置提供了其他值。
5. 忽略底部系统手势/小横条区域。归一化后默认为 36 逻辑像素，除非项目配置提供了其他值。
6. 对于全屏页面，比较公共可见高度。
7. 评估底部导航、对话框、底部弹出面板和固定底部面板时，从底部对齐底部锚定区域，但不要把系统手势条自身差异计入评分。
8. 在判定区域有问题之前，先评估小幅均匀缩放容差。因分辨率/设备缩放而整体一致偏大或偏小的候选图仍可具有高相似度。

不要让设备状态差异成为最终问题。它们是环境差异。但如果应用标题、返回按钮、搜索框、卡片、头像、列表首项等前景组件侵入真实状态栏区域，必须报告为 safe-area/overlap 缺陷；这不是状态栏图标差异，而是应用布局错误。

## 模型与脚本的角色

仅将脚本用于可复现的证据：

- 尺寸
- 归一化图像
- 热力图
- 区域条带指标
- 全局视觉相似度
- 边缘相似度
- 颜色距离
- 简单候选问题提示
- 顶部/底部忽略系统区的诊断指标，例如 `system_area_diagnostics.top_overlap_risk`
- `final_baseline_score`，在脚本层面已忽略可解释的全局缩放/分辨率差异
- 原始基线指标，仅作为证据保留

使用模型进行语义 UI 推理：

- 页面类型
- 区域边界
- 逐区域比较
- 预期锚点
- 固定 UI 与动态内容
- 全局缩放/分辨率解读
- 文字对齐/换行意图
- 遮罩和层级关系
- 顶部系统区内是否只有系统状态栏与背景/材质层，是否混入应用前景组件
- 是否有零个、一个或两个值得报告的问题

脚本不得单独驱动最终判断。低 SSIM 通常反映分辨率、JPEG 压缩、动态媒体或小幅全局缩放差异。使用 `final_baseline_score` 作为脚本级评分，因为它已应用了缩放容差。将原始 SSIM 和 `deterministic_baseline_score` 仅视为诊断证据。

## 缩放与分辨率容差

设计截图和实现截图通常具有不同的物理分辨率、设备像素比、裁切高度或预览缩放。不要仅因候选图整体一致地偏大/偏小就报告问题。

当全局缩放差异满足以下条件时视为可接受：

- 大多数区域保持了锚点
- 文字保持可读且未被裁切
- 间距关系一致
- 可见项目数量对页面类型而言实质相同
- 屏幕在正常查看尺寸下仍可读为相同 UI 状态

仅在出现具体 UI 失败时报告缩放相关问题：

- 文字或标签因控件过小而换行/裁切
- 媒体磁贴明显过高/过宽
- 底部/顶部面板不再贴合锚点
- 列表/网格因项目高度变化而显示明显不同的行数
- 全局缩放破坏了容器或导致重叠

评判缩放时，独立比较各语义区域。全屏缩放变化可以是可接受的，而单个区域与周围区域缩放不同则可能是布局缺陷。

## 页面类型

首先识别页面类型，因为权重因类型而异：

- **full_screen_app**：头部、标签栏、内容、底部导航。侧重固定 UI 和内容流。
- **list_or_grid**：重复项。侧重项目密度、行/列位置和文字换行。降低动态图片内容权重。
- **media_immersive**：图片/视频/背景为主。侧重媒体裁切、遮罩层、底部操作、亮度/透明度。
- **bottom_sheet_or_dialog**：遮罩 + 面板。侧重面板锚点、顶部圆角、内部间距、按钮位置和遮罩颜色/透明度。
- **empty_error_skeleton**：空/错误/加载页面。侧重居中定位、骨架几何和文字/按钮对齐。

## 语义检查

对每个区域检查以下属性：

- **锚点**：顶部、底部、中心或内容流。锚点失败优先级高于普通像素偏移。
- **对齐**：左、中、右、基线和网格对齐。
- **流**：整个区域是否整体偏移，内部相对布局是否保持完整。
- **层级**：遮罩是否覆盖预期区域，内容是否出现在正确层级的上方/下方。
- **文字完整性**：裁切、非预期换行、字号、标签宽度、行高和对齐。
- **媒体适配**：裁切、居中、宽高比、object-fit 以及图片磁贴是否拉伸变形。
- **样式**：颜色、亮度、透明度、模糊、渐变和阴影。

始终在区域层面执行这些检查。不要依赖全图热力图来决定问题。热力图适用于查找需要检查的候选区域，而非选择最终问题。

## 可比性

使用 `comparability` 表示两张截图是否处于相同 UI 状态：

- `0.90-1.00`：相同屏幕/状态；正常还原评分。
- `0.70-0.89`：可比，有动态内容、轻微滚动或非关键数据差异。
- `0.40-0.69`：部分可比；页面状态或滚动差异足以限制评分。
- `<0.40`：不同路由/状态；评分应视为低置信度。

不要因明确的实现布局缺陷而降低可比性。底部面板未贴合底部、列表区域起始位置过低或模态遮罩未覆盖正确区域应保持可比并作为布局问题报告。

## 首要问题选择

识别可见差异后，首先进行过滤。仅保留清晰、可在代码中定位且影响足够大的差异。对于近似匹配，返回零个问题是合理的。

然后保留最多两个。排序依据：

1. 用户可见的严重程度。
2. 问题是否影响固定 UI 或核心内容。
3. 问题是否映射到可能的代码约束。
4. 问题是否解释了多个可见症状。

优先选择根因描述而非表面比较。例如，"底部面板未锚定"优于"底部面板比设计稿高"。

不要为了凑够两个而添加第二个问题。如果剩余最强问题较轻微，则省略。
