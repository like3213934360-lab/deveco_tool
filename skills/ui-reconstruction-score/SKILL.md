## 目的

使用此技能对比设计/参考 UI 截图与代码实现/候选截图。支持同一分析流程下的两种用户意图：

- **评分**：返回稳定的还原度/相似度分数。
- **问题**：返回最多两个最明显、可操作的 UI 问题，帮助定位代码修改。

不对顶部手机状态信息区域（如时间、信号、Wi-Fi、运营商、电池或系统指示器）和底部系统手势/小横条区域进行像素评分或作为视觉差异报告。它们仅用于推断截图对齐、安全区域处理和前景组件是否侵入系统区。

## 工作流程

1. 判断输入是一对图片还是两个目录的成对截图。对于目录，按文件名主干（扩展名之前）配对图片。
2. 先直接审视图片。在查看数值分数之前，判断页面类型、主要区域，以及实现是全局缩放、全局偏移还是真正有缺陷。
3. 运行 `scripts/ui_score.py` 生成确定性证据：

```bash
python3 /path/to/ui-reconstruction-score/scripts/ui_score.py reference.png candidate.png --out report
python3 /path/to/ui-reconstruction-score/scripts/ui_score.py pic0 pic --out report --profile mobile-app --ignore-top-px 44 --ignore-bottom-px 36
```

4. 打开生成的 `report/index.html`、拼合图、归一化图像和热力图（如有）。脚本结果仅作为辅助证据。不要让低 SSIM、热力图强度或脚本提示覆盖模型可见的 UI 相似度。
5. 在评判前将 UI 划分为语义区域。这是强制要求；不要仅作为整体图像评估：
   - 忽略的顶部状态栏/系统区域和底部系统手势/小横条区域
   - 应用头部/导航
   - 固定标签栏/搜索/操作
   - 主内容流
   - 列表/网格/卡片/媒体区域
   - 遮罩层、对话框、底部弹出面板
   - 底部导航或底部锚定面板
6. 对每个语义区域，在允许小幅均匀缩放容差后进行比较。如果候选图整体一致地大 3-8% 或小 3-8%，但保持了锚点、层级、间距关系和可读性，则视为高相似度，不作为问题报告。仅在缩放导致布局破坏、文字裁切、可见项目数量显著变化或违反锚点时才报告。
7. 判断页面状态和可比性。不同的模态状态、路由、滚动位置或数据状态会降低可比性，但不要将布局约束失败误认为仅仅是可比性低。例如，底部面板出现位置过高是锚点问题，而非仅仅是滚动状态差异。
8. 根据用户请求选择输出模式：
   - 如果用户要求评分/相似度/还原质量，返回评分模式。
   - 如果用户问有什么不同、哪里需要修复或有什么问题，返回问题模式。
   - 如果用户要求完整评估，返回评分加最多三个问题。
9. 需要看图判断但宿主模型不支持多模态时，不要中止：以 `scripts/ui_score.py` 的确定性像素指标
   （相似度、边带、区域差异）为准出评分与问题，并在输出中说明本轮缺少看图证据。

## 输出模式

### 评分模式

返回紧凑评分及各维度分数。使用 0-100 分制，100 表示忽略顶部状态信息和底部系统手势/小横条区域后的截图级还原。

```json
{
  "overall": 84.2,
  "comparability": 0.93,
  "scores": {
    "state_match": 95,
    "region_alignment": 86,
    "fixed_component_layout": 82,
    "text_integrity": 88,
    "visual_style": 80,
    "media_fit": 76,
    "anchor_integrity": 90,
    "overlap_integrity": 96
  }
}
```

### 问题模式

返回零到三个问题。优先返回一个强问题而非两个弱问题，当没有明确可操作的问题时返回空列表。不包含状态栏/时间/电池/底部系统手势条本身的差异。将每个问题描述为可在代码中定位的 UI 问题，而非模糊的视觉不匹配。最终问题需综合脚本指标与看图观察两方面的证据。

使用以下结构：

```json
{
  "issues": [
    {
      "area": "底部连接面板",
      "problem": "信息面板未锚定在底部，而是位于屏幕中间，下方可见背景内容。",
      "likely_code_area": "检查底部弹出面板容器的底部定位、父视口高度、安全区域处理和层级顺序。",
      "severity": "high"
    }
  ]
}
```

在自然语言回复中，保持相同字段，但用用户使用的语言表述。

## 问题筛选规则

仅在问题通过以下所有关卡时才输出：

- 问题在正常截图查看尺寸下可见。
- 问题影响布局、可读性、层级、锚定、层级行为、媒体适配或有意义的视觉状态。
- 问题可能在代码中可操作。
- 问题不能仅由全局一致的缩放/分辨率差异解释。

如果没有问题通过这些关卡，返回 `{"issues": []}`。不要仅仅因为两张截图不是像素级一致就填充列表。

按以下优先顺序选择最明显的剩余问题：

1. 页面状态错误或缺失/多余的固定 UI，改变了屏幕含义。
2. 底部/顶部/中心锚点失败，包括底部弹出面板或面板未贴合预期边缘。
3. 顶部安全区失败：页面标题、返回按钮、搜索框、卡片、头像、列表首项等应用前景组件侵入真实状态栏区域。该问题即使发生在忽略评分的顶部系统区内，也必须作为 safe-area/overlap 问题报告。
4. 遮罩/层级失败，包括遮罩未覆盖预期区域、内容被裁切或内容出现在应覆盖它的层级之上。
5. 大区域整体偏移，如列表/网格/卡片区域整体上移或下移。
6. 文字完整性问题，包括截断、非预期换行、对齐错误、字号错误或标签宽度导致布局破坏。
7. 媒体适配问题，包括图片未居中、裁切错误、宽高比错误或网格图片拉伸变形。
8. 视觉样式问题，包括亮度、颜色、透明度、模糊或渐变差异。

当两个差异可见度相近时，优先选择更可能直接映射到代码的问题：锚定、父容器高度、内边距/外边距、弹性对齐、z-index/层级、文字换行、图片 `object-fit`、宽高比或透明度。

当整体屏幕视觉等价时，抑制小问题。被抑制的问题示例包括微小图标位置偏移、JPEG 压缩导致的轻微颜色差异、轻微的全局缩放差异以及不影响布局或可读性的个别文字抗锯齿差异。

## 问题措辞

以工程师能够定位相关代码的方式描述问题。

好的示例：

- "底部弹出面板未锚定在底部；其底边远离视口底部。"
- "网格内容起始位置过低，导致第一行未被设计中的顶部遮罩覆盖。"
- "搜索输入框过窄或内边距过大，导致查询文字被裁切。"
- "主媒体图片在其容器内向右偏移；检查图片居中或 `object-fit`。"

避免：

- "这个区域不一样。"
- "实现与设计不匹配。"
- "颜色不对"而未指明区域和可能原因。
- 任何关于时间、电池、信号或其他手机状态信息的问题。

## 评分指引

以模型可见的区域推理作为主要判断依据。使用脚本的 `final_baseline_score`、`scale_tolerant_baseline_score`、热力图和条带指标作为辅助证据。`deterministic_baseline_score` 仅作为原始证据。当原始像素指标较低但屏幕是相同 UI 且仅有全局缩放/分辨率差异时，在最终评分中忽略该差异，除非它导致具体的布局失败，如裁切、重叠、锚点错误或可见项目数量显著不同。

对于移动应用截图，推荐的默认权重为：

```text
overall =
  state_match * 0.10 +
  region_alignment * 0.18 +
  fixed_component_layout * 0.20 +
  text_integrity * 0.12 +
  visual_style * 0.12 +
  media_fit * 0.08 +
  anchor_integrity * 0.12 +
  overlap_integrity * 0.08
```

在加权评分后应用扣分：

- 关键固定元素缺失或多余：-8 至 -18
- 模态/页面状态错误：-10 至 -25，并降低 `comparability`
- 底部/顶部锚点失败：-6 至 -15
- 应用前景组件与真实状态栏重叠：-8 至 -18，并降低 `overlap_integrity`
- 文字被裁切、重叠或不可读：-5 至 -12
- 主要区域整体偏移：-4 至 -12
- 媒体裁切/宽高比明显错误：-3 至 -8
- 纯颜色/透明度差异：-2 至 -7，除非遮挡内容
