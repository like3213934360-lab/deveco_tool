# 增量式构建和功能间关联

## 增量式构建支持（可选）

⚠️ **输入参数说明**：除了标准的输入参数（功能名称、功能描述、对外提供的能力列表、代码工程理解结果）外，还支持可选的第5个参数：**已存在文档路径**

如果提供了已存在文档路径，必须读取该文档内容，并将当前功能的设计结果合并到该文档中，而不是创建新文档。

### 增量式构建流程

1. 使用 Read 工具读取已存在的设计文档
2. 分析文档结构，理解已有内容
3. 将当前功能的设计结果（代码功能实现设计、类图、时序图、工作量评估）添加到文档中
4. 更新文档的总览统计信息
5. 使用 Write 工具将更新后的内容写回已存在文档路径
6. **绝对禁止创建新文档**

## 会话管理集成（断点续传）

> **LOCAL PATCH**：上游这一节依赖 `session-manager` 和 `design-and-implementation` 两个 agent，
> 它们是 DevEco Code 自己的 agent 注册表里的条目，**本包不分发**，任何宿主上都不存在同名 agent。
> 照抄会得到「调用了一个不存在的 agent」。因此改写为宿主中立的表述：把它们当作**阶段**而不是 agent，
> 用你宿主自己的委派能力（有就委派，没有就主 agent 按同一模板顺序执行），会话状态落到设计文档本身。
> 委派能力的映射见 `manifest.json` 的 `hostToolMapping.task`。

- ⚠️ **任务开始前**：以功能名作为会话标识（如：`方案设计-用户认证`），在统一设计文档顶部建立进度区块
- ⚠️ **实时记录进度**：每个设计阶段开始和结束时把状态写回该区块
- ⚠️ **支持恢复**：任务中断后，先读回该区块判断已完成到哪一阶段，再从断点继续（允许模糊匹配不同表达方式）
- ⚠️ **合并工具调用**：批量读取文件、批量分析代码,减少轮次

### 进度区块格式

```
## 设计进度（会话：<功能名>）
- [x] 代码功能实现设计
- [ ] 类图与时序图
- [ ] 工作量评估
最后更新：<阶段描述>
```

## 标准调用格式

为确保各处发起「方案设计与代码实现」阶段时格式统一，定义以下标准输入格式。
宿主有委派能力就把它作为子任务的 prompt；没有就由主 agent 按同一模板直接执行。

### 基础格式（不使用增量式构建）

```
任务：为以下功能进行详细方案设计和代码实现
  功能名称：<功能名称>
  功能描述：<功能描述>
  对外提供的能力列表：<能力列表>
  代码工程理解结果：<代码工程理解报告内容>
```

### 增量式构建格式（推荐用于多功能点场景）

```
任务：为以下功能进行详细方案设计和代码实现
  功能名称：<功能名称>
  功能描述：<功能描述>
  对外提供的能力列表：<能力列表>
  代码工程理解结果：<代码工程理解报告内容>
  已存在文档路径：<统一设计文档路径>
  
  已实现功能关联信息：
  <可选，包含已实现功能的类/方法、可复用接口等>"
```

### 参数说明

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 功能名称 | string | 是 | 要实现的功能名称 |
| 功能描述 | string | 是 | 功能的详细描述 |
| 对外提供的能力列表 | string | 是 | 功能对外提供的接口或能力列表 |
| 代码工程理解结果 | string | 是 | code-project-understanding agent 的输出结果 |
| 已存在文档路径 | string | 否 | 统一设计文档路径，用于增量式构建 |

### 注意事项

1. **参数传递方式**：所有参数都通过 prompt 的 key-value 格式传递
2. **增量式构建**：当提供已存在文档路径时，agent 会自动执行增量式构建，将新功能设计合并到已有文档中
3. **已实现功能关联信息**：在多功能点场景下，建议传递此信息以便新功能复用已有功能
4. **格式统一**：所有 skill 调用时应保持上述格式一致

## 工作流程详细说明

### 第一步：代码功能实现设计

⚠️ **核心原则**：方案设计必须优先考虑代码复用，这是降低复杂度、提高代码质量的关键策略。

1. **深入理解相关代码文件**
   - 分析每个相关代码文件的继承关系、已实现功能等信息
   - 查找代码仓里是否有类似功能的实现及对应方案
   - 理解代码仓的架构模式和设计规范
   - ⚠️ **强制要求**：查找并读取已有功能的设计文档（模块功能设计说明书-*.md）
   - ⚠️ **强制要求**：如果已有功能设计文档包含"功能间关联信息"章节，必须仔细阅读：
     - 分析该功能依赖的已有功能
     - 分析该功能提供的可复用接口
     - 分析该功能与其他功能的数据流向
   - ⚠️ **强制要求**：分析已有功能的类、方法、调用链，识别可复用的组件
   - ⚠️ **强制要求**：在新功能设计中复用已有功能的类和方法，避免重复实现

2. **代码复用分析（强制要求）**
   - ⚠️ **强制要求**：在代码功能实现设计中必须包含"代码复用分析"章节，详细说明：
     - 可复用的现有类和方法（包括已实现功能和项目已有功能）
     - 复用方式和理由
     - 需要新增的类和方法
     - 代码改动范围评估
   - ⚠️ **强制要求**：优先复用现有代码，最小化改动范围
   - ⚠️ **强制要求**：在设计文档中明确标注"新增"、"复用"和"修改"部分

3. **列举文件修改信息**
   详细列举：
   - 当前功能需要新增的文件，以及在每个文件里需要实现的功能
   - 当前功能需要修改的现有文件，以及在每个文件里需要新增实现的功能

4. **检查实现完整性**
   - 检查是否存在实现遗漏
   - 检查是否存在重复实现
   - 确保设计方案符合架构原则

### 第二步：类图设计

1. **基于功能实现信息**
   - 基于列举的功能在各文件里的实现信息
   - 检查列举的各文件里的实现修改信息是否存在遗漏并修复
   - ⚠️ **强制要求**：在类图中明确标注新功能类与已有功能类的关系（继承、组合、依赖）
   - ⚠️ **强制要求**：使用不同的颜色或样式区分新功能类和已有功能类
   - ⚠️ **强制要求**：在类图说明中，使用表格明确列出：
     - 新功能类列表（蓝色标识）
     - 已有功能类列表（灰色标识）
     - 类之间的关系说明（每个关系的类型、方向、调用方式）

2. **输出类图**
   - 输出代码实现的详细类图（使用 Mermaid 格式）
   - 包含类之间的关系（继承、组合、依赖等）
   - 标注关键属性和方法
   - ⚠️ **强制要求**：类图中必须包含功能间的调用关系，展示完整的类依赖图
   - ⚠️ **强制要求**：在类图下方增加"功能间类关系说明"表格，详细说明：
     - 新功能类如何调用已有功能类
     - 已有功能类如何调用新功能类（如果有）
     - 类之间传递的数据类型和接口
     - 复用的已有功能组件

### 第三步：时序图设计

1. **识别实现场景**
   - 针对每个需要实现的场景输出代码实现的详细类/函数的调用关系
   - 确保覆盖所有关键流程
   - ⚠️ **强制要求**：识别功能间的调用场景，包括新功能调用已有功能、已有功能调用新功能等
   - ⚠️ **强制要求**：在时序图说明中，明确列出功能边界：
     - 新功能边界内的调用（新功能内部交互）
     - 新功能调用已有功能（跨功能调用）
     - 已有功能调用新功能（如果有）

2. **检查调用关系**
   - 检查功能实现及对应的类/函数调用关系整理是否有遗漏
   - 验证调用链的合理性
   - ⚠️ **强制要求**：验证功能间的调用关系是否合理，是否存在循环依赖等问题
   - ⚠️ **强制要求**：检查功能间调用的数据传递是否正确，数据类型是否匹配

3. **输出时序图**
   - 基于类/函数的调用关系输出每个场景代码实现的详细时序图（使用 Mermaid 格式）
   - 清晰展示交互顺序和数据流向
   - ⚠️ **强制要求**：时序图中必须包含功能间的调用，展示完整的数据流向（包括新功能与已有功能的交互）
   - ⚠️ **强制要求**：使用不同的颜色或样式区分新功能调用和已有功能调用
   - ⚠️ **强制要求**：在时序图下方增加"功能间调用说明"表格，详细说明：
     - 新功能调用的已有功能列表（功能名称、调用方法、传递参数、返回值）
     - 已有功能调用的新功能列表（如果有）
     - 功能间数据流向的详细说明
     - 功能间调用的时序和依赖关系

### 第四步：工作量评估

1. **预估代码行数**
   - 针对要实现的具体代码功能预估代码行数
   - 考虑新增文件和修改文件的代码量

2. **计算工作量**
   - 按照 500 行 1 人月的标准评估并输出当前需求的工作量
   - 提供详细的工作量分解说明

### 第五步：保存设计文档

**步骤零：增量式构建（如果提供已存在文档路径）**
- ⚠️ **强制执行**：如果提供了已存在文档路径，必须先执行增量式构建流程
- 使用 Read 工具读取已存在的设计文档
- 分析文档结构，理解已有内容
- 准备合并策略：如何将当前功能的设计结果添加到文档中
- 合并内容到文档：
  - 如果是新功能，直接添加到功能设计章节
  - 如果是已存在的功能，更新该功能的设计内容
  - 更新依赖的已有功能列表
  - 更新可被后续功能复用的接口列表
  - 更新功能间数据流向
  - 更新增增组件和接口说明
- 更新文档的总览统计信息
- 使用 Write 工具将更新后的内容写回已存在文档路径
- **绝对禁止创建新文档**

1. **整理设计内容**
   - 将代码功能实现设计、类图设计、时序图设计和工作量整理
   - 确保内容完整、格式规范
   - ⚠️ **强制要求**：按照设计规范要求（reference/design-spec.md），生成完整的9个章节内容
   - ⚠️ **强制要求**：整理功能间关联信息，包括：
     - 依赖的已有功能列表（功能名称、设计文档路径、调用的类/方法）
     - 可被后续功能复用的接口列表（类/方法名称、功能描述、调用方式）
     - 功能间数据流向（输入输出数据结构）
     - 新增的类/文件列表及其对外提供的接口

2. **保存文档**
- **如果提供了已存在文档路径**：使用 Write 工具将更新后的内容写回已存在文档路径
- **如果未提供已存在文档路径**：使用 Write 工具保存为本地文件："模块功能设计说明书-<功能名称>.md"
- ⚠️ **强制要求**：文档必须包含完整的9个章节，符合设计规范要求
- ⚠️ **强制要求**：第8章设计自检清单必须逐项填写自检状态（✅/❌/不涉及）和备注
- ⚠️ **强制要求**：使用标准化的格式记录功能间关联信息，便于后续功能点快速查找和引用

### 第六步：基于设计文档完成代码的实现（小步快跑原则）

**经验库集成（智能优化）**：
- ⚠️ **实现前查询**：在开始实现前，先调用 experience-manager agent 查询相关实现经验
- ⚠️ **优先应用经验**：优先使用高优先级、高成功率的实现经验
- ⚠️ **成功后提取**：每个小功能实现成功后，自动提取并固化经验到经验库
- ⚠️ **更新统计**：应用经验后，自动更新经验的使用统计和成功率

**重要原则**：代码修改必须遵循小步快跑原则，每次实现一个小功能，立即验证（编译验证和功能验证），避免大量修改后问题太多难以修复。

**小步定义**：小步是指实现一个可独立验证的小功能，例如：
- UI层的单个组件（如：按钮、输入框、列表等）
- 业务层的单个函数（如：数据获取、数据处理、数据验证等）
- 数据层的单个模型（如：数据结构定义、数据转换等）
- 单个调用链（如：从UI组件到业务函数到数据模型的完整调用链）

**重要**：小步的定义以功能的完整性为准，**不限制代码行数，不限制文件数量**。一个小功能可能需要修改多个文件，只要这些修改都是为了实现同一个可独立验证的功能即可。

#### 1. 修改前状态检查（强制执行）
   - ⚠️ **强制要求**：确认当前代码可编译通过
     - 必须调用 harmonyos-auto-compile skill 进行编译验证
     - 如果编译失败，必须先修复编译问题才能继续
   - ⚠️ **强制要求**：确认当前代码已提交
     - 必须执行 git status 检查
     - 如果有未提交的修改，必须先提交才能继续
   - 记录当前状态作为基准

#### 2. 按类图设计完成代码新增/修改（小步进行，强制执行）
   - **功能优先**：每次实现一个可独立验证的小功能
   - **不限制行数**：不限制代码行数，以功能的完整性为准
   - **不限制文件数**：不限制文件数量，一个小功能可能需要修改多个文件
   - 调用 harmonyos-ai-coding-skill skill 进行代码修改
   - **立即验证（强制执行）**：每次修改后立即验证（编译验证和功能验证）
     - ⚠️ **强制要求**：必须调用 harmonyos-auto-compile skill 进行编译验证
     - ⚠️ **强制要求**：编译失败必须立即停止，不得继续后续修改
     - ⚠️ **强制要求**：编译失败必须自动分析编译错误
     - ⚠️ **强制要求**：必须全量收集所有编译错误，一次性批量修复编译问题
     - ⚠️ **强制要求**：修复后必须重新执行编译验证
     - ⚠️ **强制要求**：最多重试6次，如果6次重试后仍然失败，必须停止执行并要求人工干预
     - ⚠️ **强制要求**：重试失败时，必须输出详细的编译错误信息和修复尝试记录
   - **失败即停（强制执行）**：验证失败立即停止修复，不继续后续修改
     - ⚠️ **强制要求**：必须自动分析功能验证失败的原因
     - ⚠️ **强制要求**：必须自动修复功能问题
     - ⚠️ **强制要求**：修复后必须重新执行功能验证
     - ⚠️ **强制要求**：最多重试6次，如果6次重试后仍然失败，必须停止执行并要求人工干预
     - ⚠️ **强制要求**：重试失败时，必须输出详细的功能验证失败信息和修复尝试记录
   - **验证通过后立即提交（强制执行）**：
     - ⚠️ **强制要求**：验证通过后必须立即提交代码
     - ⚠️ **强制要求**：使用正常git操作提交代码（git add . && git commit -m "描述"）
     - ⚠️ **强制要求**：提交信息必须清晰描述修改内容
     - ⚠️ **强制要求**：提交后必须执行 git status 确认提交成功
     - ⚠️ **强制要求**：如果提交失败，必须立即重试，不得继续后续修改
     - **注意**：此提交是临时检查点，最终会由外层skill通过git-commit skill合并成规范的大提交

#### 3. 按照时序图设计完成代码的调用链补全（小步进行，强制执行）
   - **单调用链优先**：每次只补全一个调用链
   - **不限制行数**：不限制代码行数，以功能的完整性为准
   - ⚠️ **强制要求**：优先补全功能间的调用链，确保新功能与已有功能能够正确交互
   - ⚠️ **强制要求**：直接调用已有功能的代码，避免重复实现已有功能
   - 调用 harmonyos-ai-coding-skill skill 补全调用链
   - **立即验证（强制执行）**：每次修改后立即验证（编译验证和功能验证）
     - ⚠️ **强制要求**：必须调用 harmonyos-auto-compile skill 进行编译验证
     - ⚠️ **强制要求**：编译失败必须立即停止，不得继续后续修改
     - ⚠️ **强制要求**：编译失败必须自动分析编译错误
     - ⚠️ **强制要求**：必须全量收集所有编译错误，一次性批量修复编译问题
     - ⚠️ **强制要求**：修复后必须重新执行编译验证
     - ⚠️ **强制要求**：最多重试6次，如果6次重试后仍然失败，必须停止执行并要求人工干预
     - ⚠️ **强制要求**：重试失败时，必须输出详细的编译错误信息和修复尝试记录
   - **检查调用完整性**：检查每个修改文件的类和函数是否被正常调用
   - ⚠️ **强制要求**：检查功能间的调用是否完整，确保新功能能够正确调用已有功能
   - ⚠️ **强制要求**：验证已有功能是否能够正确调用新功能（如果有双向调用）
   - **补全调用逻辑**：如果发现未调用的类或函数，审视设计应该在哪调用，补全调用逻辑
   - **功能验证（强制执行）**：每次修改后立即验证功能
