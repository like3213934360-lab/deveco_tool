# 设计规范要求

⚠️ **强制要求**：设计文档必须严格遵循以下规范要求，确保输出文档的完整性和规范性。

## 设计文档类型说明

根据需求类型的不同，设计文档分为以下类型，选择对应模板进行设计：

### UI 页面类型（template-ui-page.md）⚠️ **最高优先级**
   - 适用场景：结合 UX 设计稿（ArkUI DSL）与功能需求描述生成页面设计方案
   - 特点：8/10 节页面设计方案，强调 UX 设计归属映射、元素分类、布局参数提取
   - 核心章节：设计概述（归属映射）→ 页面组件架构（分类+布局）→ 状态管理 → 事件处理 → 数据模型 → 类图 → 时序图 → 文件修改清单（模式B）→ 交互设计汇总（模式B）→ 参考实现汇总（模式B）
   - 触发条件：提供了 `arkui_dsl_spec`（ArkUI DSL JSON）时自动进入此类型

### 元服务相关类型（参照华为元服务设计规范）
1. **基础框架类型**（template-basic-framework.md）
   - 适用场景：ASCF基础框架、工具链、运行时框架等底层架构需求
   - 特点：包含第零层、第一层、第二层三层设计，强调架构约束和工具编译
   - 核心章节：需求API设计、第零层/第一层/第二层设计描述、非功能设计

2. **组件类型**（template-component.md）
   - 适用场景：UI组件、自定义组件等组件开发需求
   - 特点：包含组件功能设计、竞品分析、适配规格、组件兼容性设计
   - 核心章节：需求组件设计、第零层/第一层/第二层设计描述、非功能设计

3. **高阶API类型**（template-high-level-api.md）
   - 适用场景：高阶API接口、系统能力封装等API开发需求
   - 特点：包含API功能设计、竞品API定义、模拟器支持情况、开发者文档设计
   - 核心章节：需求API设计、第零层/第一层/第二层设计描述、非功能设计

### 通用类型
4. **数据存储类型**（template-data-storage.md）
   - 适用场景：数据库、缓存、文件存储等数据存储需求
   - 特点：包含存储方案选型、数据模型设计、数据同步、数据库升级
   - 核心章节：数据存储设计、第零层/第一层/第二层设计描述、非功能设计

5. **网络通信类型**（template-network.md）
   - 适用场景：HTTP请求、WebSocket、消息推送等网络通信需求
   - 特点：包含网络架构设计、接口设计、弱网优化、安全性设计
   - 核心章节：网络架构设计、第零层/第一层/第二层设计描述、非功能设计

6. **多媒体类型**（template-multimedia.md）
   - 适用场景：音频、视频、图片、摄像头等多媒体需求
   - 特点：包含格式支持、播放控制、性能优化、功耗优化
   - 核心章节：多媒体设计、第零层/第一层/第二层设计描述、非功能设计

7. **设备能力类型**（template-device-capability.md）
   - 适用场景：传感器、蓝牙、NFC、定位等设备能力需求
   - 特点：包含设备抽象、数据采集、权限管理、隐私安全
   - 核心章节：设备能力设计、第零层/第一层/第二层设计描述、非功能设计

8. **通用类型**（design-template.md）
   - 适用场景：其他类型需求或作为备用模板
   - 特点：包含完整的9个章节模板结构、标准化表格格式、设计自检清单
   - 核心章节：系统与架构视图、模块详细设计、接口设计、数据设计、非功能设计

### 类型判断规则
在进行方案设计前，需要根据需求描述判断需求类型，选择对应的模板：

**判断优先级（P0 最高）：**

1. **UI 页面类型（P0）**：提供了 `arkui_dsl_spec`（ArkUI DSL JSON）→ 使用 `template-ui-page.md`
2. **元服务相关类型（P1）**：需求涉及 ASCF 基础框架、UI 组件、高阶API
3. **通用类型（P2）**：数据存储 / 网络通信 / 多媒体 / 设备能力
4. **通用类型（P3）**：其他需求 → 使用 `design-template.md`

## 文档级别要求
- 软件实现设计需要分层分级，一般分两个级别：L0为SDK/组件/应用级，L1为模块级
- 要求具备可继承性，随版本持续更新演进
- 如果当前没有，先针对当前特性设计，按模板输出

## 必选（M）、条件必选（C）和可选（O）说明
- **M（必选）**：必须提供的内容，不得遗漏
- **C（条件必选）**：根据实际情况，如果涉及则必须提供
- **O（可选）**：根据需要选择性提供

## 各章节详细要求

### 第1章 文档基本信息
- **文档标题与标识（M）**：格式为 [领域]-[SDK/组件/应用]-[L0]-[L1]-[系统版本.小版本]，例如：大桌面领域-SceneBoard-Launcher-SmartDock-v6.0.1
- **修订历史（M）**：记录日期、版本、作者、修改描述、审核人；每次评审后修改必须记录，重点对修改进行描述
- **术语表/名词解释（C）**：涉及业务相关专用术语缩写时必选，通用术语可选
- **参考文档（M）**：列出需求文档、UI设计稿、依赖的第三方库、API接口文档、竞品开发者文档链接等

### 第2章 系统与架构视图
- **架构设计图（M）**：展示架构设计和分层（UI层、业务逻辑层、数据层、基础组件层），标注模块间依赖、通信方式等
- **关键业务框架及约束（M）**：展示关键业务框架设计，阐述业务分层设计、组件复用、异步/并发设计等关键开发原则
- **外部依赖（M）**：明确平台框架依赖、三方库依赖、硬件依赖、模型依赖等外部依赖
- **设备适配策略（C）**：若涉及多设备（手机/平板/折叠屏）或不同屏幕尺寸/分辨率，需说明适配方案（动态布局、配置隔离、多目标构建等）
- **跨平台桥接设计（C）**：若SDK需支持Flutter/React Native等跨平台环境，需设计桥接层架构，明确双向通信协议、线程模型、资源管理
- **竞品分析（C）**：竞品实现方案分析对比，优劣势分析

### 第3章 模块详细设计
- **UI组件设计（C）**：涉及UI时必选。自定义View/ViewController的职责、界面布局抽象、交互逻辑等，对于可复用UI组件需提供使用示例
- **业务逻辑流程（M）**：核心业务逻辑的流程图/状态机，包含正常流程及异常分支（网络超时、权限拒绝、服务端错误）
- **异步及线程模型（M）**：明确耗时操作（网络请求、IO、计算）的处理策略（异步/线程等），以及回到主线程更新UI的方式
- **部署及运行模型（M）**：模块部署形态，是否涉及多进程、多线程、多实例等运行情况，如涉及需要考虑代码及资源共享问题
- **生命周期管理（M）**：应用、组件等生命周期管理；如何处理组件复用、屏幕旋转、配置变更、内存告警等事件；如何防止内存泄漏（取消订阅、释放资源）
- **其他（O）**：若模块间采用事件总线（如EventBus等），需定义事件类型、发布/订阅规则、取消订阅时机；若涉及特性隔离，可以采用多目标构建、编译宏、特性开关、CCM配置隔离等方式

### 第4章 接口设计
- **对外API设计（M）**：SDK/组件必选。命名清晰符合平台惯例；参数简洁；返回值及错误码统一；提供详细的API文档及示例代码；标注是否可能抛出异常
- **回调/委托设计（M）**：异步操作结果通过回调/监听器/闭包返回时机及时序；提供取消回调的机制；防止重复回调
- **跨进程通信IPC（C）**：若模块需要与其它进程通信，需定义接口文件、数据序列化方式、线程模型及异常处理
- **隐式意图/通用链接（C）**：若需通过外部唤起或与其他App交互，需定义scheme/path规则、参数解析、安全验证（校验来源）

### 第5章 数据设计
- **业务数据模型设计（M）**：业务数据模型，定义业务本体概念，对应代码中的数据类，界面无关。必须包含此内容设计，例外需说明
- **本地存储方案（C）**：如需持久化数据，需说明存储方式（Preferences/文件/数据库），以及数据备份、克隆、升级策略（升级表结构）
- **数据库设计（C）**：需提供完整的ER图或表结构定义，说明索引设计、事务使用、预填充数据库方案
- **缓存设计（O）**：内存缓存（LRU Cache）或磁盘缓存的设计，包括缓存大小限制、缓存一致性、键值命名规范
- **敏感数据保护（M）**：明确哪些数据属于敏感信息（密码、令牌、生物特征、个人隐私数据等），禁止明文打印，存储必须加密，安全传输协议

### 第6章 非功能性设计
- **性能设计（M）**：
  1. 启动性能：冷启动时间优化措施（懒加载、异步初始化）
  2. UI流畅度：避免主线程耗时操作，减少布局层级，避免过度绘制，数据缓存、预加载等
  3. 内存：预估内存占用，避免内存泄漏，按需动态加载，提供内存警告处理策略
  4. 包体积：代码混淆，动态库瘦身，按需加载模块，图片资源优化
- **功耗设计（O）**：
  1. 前台UI：只做必要的事情，适时停止，按需使用资源。减少过度绘制、避免不必要的刷新，使用合适的动效等
  2. 后台任务：定位、网络轮询等，需考虑电量消耗，使用节能API，避免频繁唤醒CPU
- **网络设计（C）**：
  1. 网络请求：统一网络层，超时设置，重试机制，缓存策略
  2. 弱网优化：请求合并、数据压缩、断点续传、预加载
  3. 网络状态变化：监听网络连通性/类型切换，自动重试失败的请求，提示用户无网络
- **安全设计（M）**：
  1. 代码混淆：启用混淆，防止逆向
  2. 外部输入：外部输入安全校验
  3. 权限申请：只申请需要的权限；当真正需要时动态申请权限
  4. 高风险API：权限控制，必须覆盖DT-Fuzz
- **隐私合规（M）**：
  1. 数据收集声明：明确收集哪些个人信息（设备信息、位置）、用途及共享情况
  2. 用户同意机制：在首次启动或必要时机弹出隐私协议授权，用户拒绝后的降级处理
  3. 权限说明：为每个权限提供使用说明字符串（如"用于扫描附近蓝牙设备以连接智能家居"）
- **调试与定位（M）**：
  1. 日志：正式版本需关闭DEBUG日志；日志输出需脱敏（隐藏Token、密码）；避免无效日志输出
  2. 调试开关：提供必要的业务调试开关，默认关闭
  3. 打点：trace打点、用户行为打点、故障打点等
  4. DT用例设计：有效的DT用例设计功能覆盖
- **国际化与本地化（O）**：若应用需支持多语言，需提取所有字符串资源，按平台规范放置，并提供RTL布局适配（如需）
- **适老化与无障碍（O）**：若应用需要支持适老化与无障碍，需按实现对应功能

### 第7章 SDK/组件特有设计
- **初始化设计（M）**：SDK必选。明确初始化时机，是否需传入Context，是否支持多进程初始化。初始化失败的处理
- **依赖管理（M）**：列出所有依赖的第三方库及版本，说明是否存在版本冲突风险及解决方案
- **SDK版本兼容（M）**：定义版本号规范（语义化版本），说明API废弃策略，保证主版本升级时的向后兼容性
- **集成文档（M）**：提供详细集成文档（README），包含接入步骤、权限声明、代码示例、常见问题

### 第8章 设计自检及CodeReview清单
- **强制要求**：设计人自填，确保覆盖常见问题，自检状态填✅/❌/不涉及，CodeReview依据此范围规格进行检视确认
- 必须包含所有检查项：文档基本信息、架构设计、模块设计、接口设计、数据设计、性能设计、网络设计、安全设计、隐私合规、调试与定位、SDK特有设计、其他等

### 第9章 功能间关联信息（增量设计）
- **依赖的已有功能**：功能名称、设计文档路径、调用的类/方法、调用方式、数据传递
- **可被后续功能复用的接口**：类/方法名称、功能描述、调用方式、输入参数、返回值、使用示例
- **功能间数据流向**：数据流名称、起始功能、终止功能、数据结构、流向说明
- **新增组件和接口说明**：组件/接口名称、类型、功能描述、对外提供的接口、可被复用性

**功能间拉通设计原则**：
- ⚠️ **强制要求**：设计新功能时必须分析已有功能的设计和实现，确保功能间调用关系清晰
- ⚠️ **强制要求**：新功能设计必须基于已有功能进行增量设计，不得独立设计
- ⚠️ **强制要求**：时序图中必须包含功能间的调用关系，展示完整的数据流向
- ⚠️ **强制要求**：复用已有功能的类和方法，避免重复实现
- ⚠️ **强制要求**：在类图中明确标注新功能与已有功能的类关系（继承、组合、依赖）
- **实现方式**：
  1. 设计前读取已有功能的设计文档（模块功能设计说明书-*.md）
  2. 分析已有功能的类、方法、调用链
  3. 在新功能设计中复用已有功能的类和方法
  4. 在时序图中展示新功能如何调用已有功能
  5. 在代码实现时直接调用已有功能的代码，避免重复实现

**功能间设计文档传递机制**：
- ⚠️ **强制要求**：每个功能点设计完成后，必须生成"功能间关联摘要"，包含：
  - 新增的类/文件列表及其对外提供的接口
  - 新增的方法及其调用关系
  - 与已有功能的调用关系（调用哪些已有功能、被哪些功能调用）
  - 可供后续功能复用的组件和方法
- ⚠️ **强制要求**：在当前功能点的设计文档末尾，增加"功能间关联信息"章节，明确列出：
  - 依赖的已有功能（功能名称、设计文档路径、调用的类/方法）
  - 可被后续功能复用的接口（类/方法名称、功能描述、调用方式）
  - 功能间数据流向（输入输出数据结构）
- ⚠️ **强制要求**：使用标准化的格式记录功能间关联信息，便于后续功能点快速查找和引用
- ⚠️ **强制要求**：在类图中使用不同颜色区分新功能类（蓝色）和已有功能类（灰色），并标注功能间的调用关系
- ⚠️ **强制要求**：在时序图中使用不同的样式区分新功能调用（实线）和已有功能调用（虚线），并标注功能边界

## 案例分析

### 案例1：网络通信类型设计文档示例

**需求**：为应用添加HTTP网络请求功能，支持GET、POST请求，具备超时和重试机制

**设计文档类型判断**：网络通信类型 → 使用 template-network.md

**设计文档关键章节示例**：

### 第2章 系统与架构视图

**架构设计图**：
```
┌─────────────────────────────────────┐
│           UI Layer                   │
│  (ProductListPage, OrderPage, ...)   │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│        Business Layer               │
│  (ProductService, OrderService)     │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│      Network Layer (新增)           │
│  HttpClient, RequestInterceptor     │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│      Platform Layer                 │
│  @ohos.net.http                     │
└─────────────────────────────────────┘
```

**关键业务框架及约束**：
- 统一网络层：所有网络请求通过 HttpClient 发送
- 拦截器模式：使用拦截器处理通用逻辑（认证、日志、错误处理）
- 异步处理：网络请求必须异步执行，不阻塞主线程

### 第3章 模块详细设计

**业务逻辑流程**：
```
1. 业务层调用 HttpClient.request()
2. 请求拦截器预处理（添加Token、签名）
3. 发送HTTP请求
4. 响应拦截器后处理（错误处理、数据转换）
5. 返回结果给业务层
```

**异步及线程模型**：
- 使用 Promise 模式处理异步请求
- 网络请求在后台线程执行
- 通过 async/await 简化异步代码

### 第4章 接口设计

**对外API设计**：
```typescript
class HttpClient {
  // 发送GET请求
  get<T>(url: string, params?: Record<string, any>): Promise<T>
  
  // 发送POST请求
  post<T>(url: string, data?: any): Promise<T>
  
  // 发送PUT请求
  put<T>(url: string, data?: any): Promise<T>
  
  // 发送DELETE请求
  delete<T>(url: string): Promise<T>
}
```

### 第6章 非功能性设计

**网络设计**：
- 超时设置：默认30秒，可配置
- 重试机制：失败后自动重试3次，指数退避
- 弱网优化：支持请求压缩、断点续传

**安全设计**：
- HTTPS：生产环境强制使用HTTPS
- 证书校验：启用SSL证书校验
- 敏感数据：Token、密码等敏感数据不在日志中打印

### 第5章 数据设计

**数据库设计**：

**用户表（users）**：
| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| id | INTEGER | PRIMARY KEY | 主键 |
| username | TEXT | UNIQUE, NOT NULL | 用户名 |
| password | TEXT | NOT NULL | 密码（加密） |
| email | TEXT | UNIQUE | 邮箱 |
| created_at | INTEGER | NOT NULL | 创建时间戳 |

**商品表（products）**：
| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| id | INTEGER | PRIMARY KEY | 主键 |
| name | TEXT | NOT NULL | 商品名称 |
| price | REAL | NOT NULL | 价格 |
| stock | INTEGER | NOT NULL | 库存 |
| created_at | INTEGER | NOT NULL | 创建时间戳 |

**索引设计**：
- users表：username字段建立唯一索引
- products表：name字段建立普通索引

**数据库升级策略**：
- 版本1：创建users表
- 版本2：创建products表
- 版本3：为products表添加索引
