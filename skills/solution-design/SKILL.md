# Solution Design Agent

此 skill 提供技术方案设计能力，支持两种模式：
- **通用模块设计模式**：以代码文件和功能需求为输入，生成模块功能设计说明书
- **UI 页面设计模式**：以 UX 设计稿（ArkUI DSL）与功能需求描述为输入，生成页面设计方案

## 项目配置

⚠️ **优先级最高**：在执行任何操作之前，必须先检查项目根目录的 `AGENTS.md` 文件，加载项目特定的配置。

### 配置加载流程
1. 读取项目根目录的 `AGENTS.md` 文件
2. 查找 `solution-design-skill` 相关配置
3. 加载项目特定的配置项

### AGENTS.md 配置示例
```markdown
## solution-design-skill

### custom_templates
- `templates/custom-framework.md` - 项目框架类型设计文档模板
- `templates/custom-component.md` - 项目组件类型设计文档模板

### coding_standards
- skill: arkts-standards  # 使用的编码规范skill
- reference: reference/arkts-standards.md  # 编码规范参考文档
```

### 配置项说明
- `custom_templates`：项目定制的设计文档模板列表（可选）
- `coding_standards`：项目编码规范配置（可选）

### 配置优先级
1. 项目 AGENTS.md 定制的配置（最高优先级）
2. skill 默认配置
3. 通用配置

## 模式一：UI 页面设计模式（P0）

> 当提供了 `arkui_dsl_spec`（ArkUI DSL JSON）时，自动进入此模式。

### 输入参数

| 参数 | 必需 | 说明 |
|------|------|------|
| `arkui_dsl_spec` | ✅ | ArkUI DSL JSON，含 `ui.children[]` 嵌套树、`meta.bbox`、`layoutStrategy`、`responsive`、`breakpoints` |
| `task_description` | ✅ | 功能需求描述的全集概述 |
| `functional_spec` | - | 用户补充的功能规格（可为空） |
| `use_hds` | - | 是否使用 HDS 组件（UI Design Kit） |
| `immersive_light_spec` | - | 沉浸光感需求，可为 `true` / `false` / `auto` / 结构化对象；当需求中出现"沉浸光感"、"沉浸式"、"动态模糊"、"悬浮"、"毛玻璃"、"HDS 6.1"等关键词时按 `auto` 处理 |
| `hds_capability_profile` | - | HDS/API 可用性约束：`public_only` / `internal_allowed` / `unknown`，用于决定是否允许写入 `systemMaterialEffect`、`hdsMaterial` 等材质配置，默认 `unknown` |
| `selected_practices` | - | 用户选中的最佳实践列表（可为空） |
| `repo_context` | - | 代码仓上下文信息（存量增强时提供，含存量组件清单、差异分析等） |
| `save_path` | - | 设计文档保存路径，默认保存到 `{projectRoot}/.codegenie/{saveName}/stage5.design-doc.md` |
| `incremental` | - | 是否为增量设计（提供已有设计文档路径时为 true） |

### 核心设计原则

**UX 设计稿不是功能全集，而是功能全集的一个具体视觉实现示例。**

- UX 设计稿可能只覆盖需求功能描述中的**某个关键场景**（而非全部功能点）
- UX 设计稿中可能包含**来自其他功能模块的界面元素**（用于展示当前功能在整体界面中的位置）
- 方案设计必须以功能需求描述（`task_description`）为全集，UX 设计稿为视觉参考，两者结合确定最终实现范围

### UI 页面设计工作流程

#### 第一步：理解 UX 设计稿的归属范围

**目标**：确定 UX 设计稿对应功能需求描述的哪个部分。

1. **阅读功能需求描述**（`task_description` + `functional_spec`）
   - 理解要实现的功能全集
   - 识别功能的边界：哪些是当前需求要实现的核心功能，哪些是关联功能

2. **分析 UX 设计稿**
   - 遍历 `arkui_dsl_spec` 的 `ui.children[]` 嵌套树
   - 理解整个页面的布局结构和所有可见元素

3. **建立归属映射**

   回答以下问题并在设计文档中记录：
   - UX 设计稿展示的是哪个功能场景？（可能是功能全集的一个子集或关键路径）
   - UX 设计稿中的每个主要区域/页面，对应需求描述中的哪个功能点？
   - 如果 UX 设计稿只展示了部分功能，确认其余功能的设计策略（后续迭代/不在本次范围）

   **归属映射表**（在 §1 设计概述中记录）：

   | UX 区域/场景 | 对应需求功能点 | 是否在本次实现范围 | 设计策略 |
   |-------------|--------------|-------------------|---------|
   | 主内容区 | [功能点A] | ✅ 是 | 按 UX 设计实现 |
   | 底部导航 | [功能点B] | ❌ 否（存量） | 保持不变 |
   | 侧边栏 | [功能点C] | ✅ 是（修改） | 在存量基础上适配 |

#### 第二步：元素分类与来源分析

**目标**：对 UX 设计稿中的每个界面元素进行分类，确定实现策略。

对 `arkui_dsl_spec` 嵌套树中的每个节点，按以下分类进行标注：

| 分类 | 含义 | 设计处理 |
|------|------|---------|
| **新增** | 当前功能要新实现的界面元素 | 按 UX 设计完整实现 |
| **修改** | 已有但需要调整的界面元素（模式B，或模式A中 UX 设计与需求有差异的部分） | 分析差异，按需调整 |
| **复用** | 已实现且无需修改的界面元素（模式B存量代码，或 UX 中的装饰性/占位元素） | 保持不变 |
| **无关** | 来自其他功能模块的界面元素（用于展示界面上下文，非本次实现范围） | 不实现，标注说明 |

**元素分类表**（在 §2 页面组件架构中作为组件树节点标注）：

| 节点 ID | 组件类型 | 分类 | 说明 |
|---------|---------|------|------|
| `L0-0` | Column | 新增 | 主内容区容器 |
| `L0-1` | Row | 无关 | 顶部导航栏（属于导航模块，本次不实现） |
| `L1-0` | Text | 新增 | 标题文字 |
| `L1-1` | Button | 修改 | 提交按钮（存量样式需适配新配色） |
| ... | | | |

**HDS 决策与沉浸光感设计**：`solution-design` 是 `hdsRequired`、HDS 候选区域、HDS 组件替换映射和沉浸光感设计的唯一决策来源。生成 UI 页面设计文档前必须读取 `assets/template-ui-page.md`，并按其中 §2.3、§2.4 填写字段。

必须执行以下门禁：

- 当 `use_hds` 为 true、用户明确要求 HDS、需求/设计稿出现沉浸光感/沉浸式/动态模糊/悬浮材质/HDS 风格导航页签操作栏，或仓内已有 HDS 使用痕迹时，默认输出 `hdsRequired: true` 和 HDS 候选组件映射。
- 禁止用缺少包声明、标准 ArkUI fallback 足以近似、主观 SDK 猜测、后续可增量引入、避免兼容性问题等理由输出 `hdsRequired: false`。
- API 可用性未知时，输出 `hdsRequired: true`、候选组件、待第四阶段 import/构建验证项；不要提前降级。
- 只有用户明确要求不用 HDS、设计稿/需求/仓内均无 HDS 候选，或已有 import/构建/类型检查失败证据且用户批准降级时，才允许输出 `hdsRequired: false`。
- 当触发沉浸光感时，必须填写模板 §2.4，明确节点、目标组件/方案、滚动绑定、API 可用性、降级策略和验收标准；不要只写“使用沉浸光感”。

#### 第三步：提取界面实现参数

**目标**：从 UX 设计稿中提取驱动代码生成的所有参数。

从 `arkui_dsl_spec` 的每个节点中提取以下信息，填入对应设计章节：

**§2 页面组件架构 — 布局参数**：

| 节点 | 容器类型 | 布局方向 | 对齐 | 间距 | 响应式尺寸 | bbox |
|------|---------|---------|------|------|-----------|------|
| `L0-0` | `Column` | 垂直 | 顶部+水平居中 | gap: 16 | width: 100%, height: auto | [0,0,375,667] |
| `L1-0` | `Row` | 水平 | 两侧分散 | gap: 8 | width: 100%, height: 48 | [0,0,375,48] |

- 容器类型 ← `layoutStrategy.type`（flex/grid/stack）
- 布局方向 ← `layoutStrategy.direction`
- 对齐 ← `layoutStrategy.alignment`
- 间距 ← `layoutStrategy.gap`
- 响应式尺寸 ← `responsive.width.type` / `responsive.height.type`
- bbox ← `meta.bbox`

**§3 状态管理设计 — 交互组件识别**：

| 组件 | 状态变量 | 装饰器 | 状态来源/触发 | 流向 |
|------|---------|--------|-------------|------|
| Toggle | `isEnabled` | @State | 用户点击 | Toggle → 影响列表显示 |
| Button | - | - | 点击触发网络请求 | Button → Service → 更新状态 |
| TextInput | `inputText` | @State | 用户输入 | TextInput → 校验 → 按钮可用性 |

- 从 `arkui_dsl_spec` 的交互组件（Toggle、Button、TextInput、Checkbox、Slider、Select 等）识别状态变量
- 区分 `@State`（组件内私有）、`@Prop`（父传子）、`@Link`（双向同步）
- 参照 `repo_context.stateManagementPattern` 保持存量模式一致（模式B）

**§4 事件处理与交互设计**：

| 事件 | 触发条件 | 处理逻辑 | 导航跳转 | 组件联动 |
|------|---------|---------|---------|---------|
| onClick | Button 点击 | 提交表单数据 | router.pushUri('pages/Result') | 同时显示 loading |
| onChange | Toggle 切换 | 切换功能开关 | - | 联动刷新列表 |
| onSubmit | TextInput 提交 | 搜索请求 | - | 触发列表刷新 |

- 从 `functional_spec`（用户补充的交互行为描述）中提取
- 若 `functional_spec` 为空，从 UX 设计稿的组件类型和 `selected_practices` 推断最小交互

**§5 数据模型设计**：

| 数据模型 | 字段 | 类型 | 数据源 | 用途 |
|---------|------|------|--------|------|
| `PageData` | items, total, page | `Item[]`, `number`, `number` | 网络请求 | 列表数据 |
| `Item` | id, title, status | `string`, `string`, `boolean` | 来自 `PageData` | 列表项 |

- 从 `arkui_dsl_spec` 的 `content`（文本）、`src`（图片路径）中推断数据模型字段
- 标注数据源类型：静态硬编码 / 网络请求 / 本地存储 / 计算派生

#### 第三步补充：动效设计参数提取

**目标**：从功能需求描述和交互设计中提取所有动效需求，转化为 ArkUI 可实现的动效规格。

⚠️ **强制要求**：当功能需求中包含"动效"、"动画"、"过渡"、"转场"、"渐入"、"渐出"、"滑动"等关键词时，必须填写以下三个动效表格。仅写"添加渐进渐出动效"等一句话描述是不够的，必须明确到 ArkUI API 级别。

**§4.5 动效详细规格表**（在 §4 事件处理与交互设计中记录）：

| 动效ID | 动效名称 | 触发事件 | 动效类型 | 持续时间 | 缓动曲线 | 动画属性 | 起始值→结束值 | 延迟 | 循环模式 |
|--------|---------|---------|---------|---------|---------|---------|-------------|------|---------|
| A01 | Tab切换渐入渐出 | selectedIndex变化 | 透明度渐变 | 200ms(出)+200ms(入) | EaseInOut | opacity | 1→0→1 | 0ms(出),200ms(入) | 单次 |
| A02 | 页面进入转场 | pushPathByName | 位移+透明度 | 300ms | EaseOut | translateX+opacity | 100%+0→0+1 | 0ms | 单次 |
| A03 | 收藏按钮切换 | onClick | 缩放+颜色 | 150ms | Spring | scale+fillColor | 1→1.2→1 / 灰→红 | 0ms | 单次 |

动效类型枚举：透明度渐变(fade) / 位移滑动(slide) / 缩放(scale) / 旋转(rotate) / 颜色过渡(color) / 组合(combined)

**§4.6 ArkUI 动效实现方案**（在 §4 事件处理与交互设计中记录）：

| 动效ID | 推荐 ArkUI API | 需要的状态变量 | 触发机制 | 实现要点 | 已知坑点 |
|--------|---------------|--------------|---------|---------|---------|
| A01 | `.animation()` + `@Monitor` | `@Local tabOpacity: number` | `@Monitor('selectedIndex')` 中设 opacity=0，setTimeout 后设为1 | Tabs 需设 `scrollable(false)` + `animationDuration(0)`，用 opacity 做渐变 | `animationDuration` 仅在 `scrollable(true)` 时生效；`scrollable(false)` 时此属性无效，必须自定义动画 |
| A02 | Navigation `customNavContentTransition` | 无（系统管理） | 系统自动触发 | 在 Navigation 上配置 `customNavContentTransition` 回调，返回自定义动画对象 | 需实现 `AnimatedTransition` 接口；返回 undefined 则使用默认转场 |
| A03 | `.animation()` + `@Local` | `@Local isFavorite: boolean` | onClick 翻转状态 | 对 Image 添加 `.scale()` 和 `.fillColor()`，绑定 `.animation()` | fillColor 动画需 Image 已设置 fillColor 才生效；Spring 曲线无法用 `.animation()` 实现，需用 `animateTo` |

**ArkUI 动效 API 选择决策树**：

```
是否需要响应用户交互触发？
├─ 是 → 状态变化驱动动画
│   ├─ 单属性简单动画 → `.animation()` 修饰符 + @Local/@Monitor
│   ├─ 多属性编排动画 → `animateTo()` 闭包内修改多个状态
│   └─ 弹性/物理动画 → `animateTo({ curve: Curve.Spring })` 或 `springMotion()`
└─ 否 → 系统自动触发
    ├─ 页面进入/退出转场 → Navigation `customNavContentTransition`
    ├─ 组件出现/消失动画 → `.transition()` + `if/else` 条件渲染
    └─ 列表项增删动画 → `List` 的 `.animateItemDuration()`
```

**§4.7 动效时序图**（在 §4 事件处理与交互设计中记录）：

对每个动效输出基于文本的时间轴，明确每个时间点的状态变化和视觉表现：

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- 总时长标注

##### 时序图

**§7 时序图**：

基于第三步的事件处理设计，输出关键交互场景的 Mermaid 时序图。

## 模式二：通用模块设计模式（P1-P3）

> 当未提供 `arkui_dsl_spec` 时，进入此模式，按原有流程执行。

### 第一步：代码功能实现设计

⚠️ **核心原则**：方案设计必须优先考虑代码复用，这是降低复杂度、提高代码质量的关键策略。

1. **深入理解相关代码文件**
   - 分析每个相关代码文件的继承关系、已实现功能等信息
   - 查找代码仓里是否有类似功能的实现及对应方案
   - 理解代码仓的架构模式和设计规范
   - ⚠️ **强制要求**：查找并读取已有功能的设计文档（模块功能设计说明书-*.md）
   - ⚠️ **强制要求**：如果已有功能设计文档包含"功能间关联信息"章节，必须仔细阅读
   - ⚠️ **强制要求**：分析已有功能的类、方法、调用链，识别可复用的组件
   - ⚠️ **强制要求**：在新功能设计中复用已有功能的类和方法，避免重复实现

2. **代码复用分析（强制要求）**
   - ⚠️ **强制要求**：在代码功能实现设计中必须包含"代码复用分析"章节
   - ⚠️ **强制要求**：优先复用现有代码，最小化改动范围
   - ⚠️ **强制要求**：在设计文档中明确标注"新增"、"复用"和"修改"部分

3. **列举文件修改信息**
   - 当前功能需要新增的文件，以及在每个文件里需要实现的功能
   - 当前功能需要修改的现有文件，以及在每个文件里需要新增实现的功能

4. **检查实现完整性**
   - 检查是否存在实现遗漏
   - 检查是否存在重复实现
   - 确保设计方案符合架构原则

### 第二步：类图设计

1. **基于功能实现信息**
   - ⚠️ **强制要求**：在类图中明确标注新功能类与已有功能类的关系
   - ⚠️ **强制要求**：使用不同的颜色或样式区分新功能类和已有功能类
   - ⚠️ **强制要求**：在类图说明中列出新功能类列表（蓝色标识）和已有功能类列表（灰色标识）

2. **输出类图**（Mermaid 格式）
   - ⚠️ **强制要求**：类图中必须包含功能间的调用关系
   - ⚠️ **强制要求**：在类图下方增加"功能间类关系说明"表格

### 第三步：时序图设计

1. **识别实现场景**
   - ⚠️ **强制要求**：识别功能间的调用场景
   - ⚠️ **强制要求**：在时序图说明中明确列出功能边界

2. **检查调用关系**
   - ⚠️ **强制要求**：验证功能间的调用关系是否合理
   - ⚠️ **强制要求**：检查功能间调用的数据传递是否正确

3. **输出时序图**（Mermaid 格式）
   - ⚠️ **强制要求**：时序图中必须包含功能间的调用
   - ⚠️ **强制要求**：在时序图下方增加"功能间调用说明"表格

### 第四步：工作量评估

1. **预估代码行数**：考虑新增文件和修改文件的代码量
2. **计算工作量**：按照 500 行 1 人月的标准评估

### 第五步：保存设计文档

1. **整理设计内容**：确保内容完整、格式规范
2. **判断输出路径**：
   - 若提供已存在文档路径，增量合并
   - 若未提供，使用 Write 工具保存为"模块功能设计说明书-<功能名称>.md"
3. ⚠️ **强制要求**：文档必须包含完整的 9 个章节
4. ⚠️ **强制要求**：设计自检清单必须逐项填写

## 注意事项

1. **需求类型判断优先**：在执行任何设计步骤之前，必须先判断需求类型（UI 页面 / 元服务 / 数据存储 / 网络通信 / 多媒体 / 设备能力 / 通用）
2. **代码复用优先**：通用模块设计模式必须优先考虑代码复用
3. **UX 设计稿与功能需求的映射**：UI 页面设计模式必须先建立归属映射，再进行元素分类，最后提取实现参数
4. **设计规范**：确保设计方案符合设计规范要求
5. **增量式构建**：支持增量式构建，可将多个功能点的设计合并到统一文档中
6. **功能间关联**：详细记录功能间关联信息，便于后续功能点快速查找和引用
7. **类型定义**：根据编码规范要求，在设计文档中包含完整的类型定义
8. **动效设计强制要求**：当功能需求中包含动效相关描述时，必须填写 §4.5 动效详细规格表、§4.6 ArkUI 动效实现方案、§4.7 动效时序图。仅写"添加渐进渐出动效"等一句话描述是不够的，必须明确到 ArkUI API 级别，包括：动效类型、持续时间、缓动曲线、推荐 API、状态变量、触发机制、已知坑点。特别注意 ArkUI 组件限制（如 Tabs 的 `animationDuration` 在 `scrollable(false)` 下无效），需在"已知坑点"列标注。
