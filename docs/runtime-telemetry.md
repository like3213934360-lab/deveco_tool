# 日常性能日志与 UI 流程复用

0.4.0 的本次修订补齐失败请求的 `elapsed_ms`，包含取消和工作线程拒绝的请求。开始、返回和失败事件都携带 `instance_id`，便于与同一个运行实例的内存样本关联。`request_finish` 只表示工具返回，业务成功仍需检查 `outcome`、运行状态和验证证据。

工作线程启动、每 60 秒和关闭清理前写一条 `runtime_sample`。记录 RSS、工作线程堆、external/ArrayBuffer 内存、当前请求数及已跟踪的进程、连接、解析器和 UI 缓存计数，不启动额外采集进程，不强制 GC，不记录请求正文、路径、口令或界面文字。RSS 属于整个 Node 进程，其余内存计数属于采样的运行工作线程；不包含独立 SDK 子进程内存。

所有实例在同一状态库最多保留 2880 条内存样本，也受已有的普通事件数量和时间保留策略约束；多个实例会缩短实际覆盖时长。写入受共享存储配额限制。失败样本直接丢弃，不积压重试；连续故障只在 stderr 报告一次 `runtime_sample_failed`，恢复后下一条样本保留累计失败数和序号缺口。采样失败不阻断工具或存储恢复操作，退出时清除定时器。

在开发目录运行只读脚本，按用户需要检查增量日志：

```sh
python3 scripts/runtime-log-review.py --state /absolute/state --after-event-id 12345
```

下次使用返回的 `through_event_id`。输出分开统计返回/失败耗时、旧日志缺少耗时的数量、各运行实例的内存起止值和峰值、无已跟踪请求/进程/解析器/LSP 活动时的样本，以及 `ui_flow` 各动作和通过 `workflow_run` 启动流程的次数。不要跨实例拼接趋势。内存上涨、单个峰值或调用次数都不能单独证明泄漏、性能改善或错过了适合回放的场景。构建警告须继续检查被引用的构建日志，宿主启动和传输异常须检查宿主 stderr。

UI 复用指引现在通过 MCP 初始化说明、`ui_flow`、`ui_query`、`ui_control` 的描述以及 debug/UI 测试方法和内置 Skill 提供。多步导航、返回已访问页面或重复复现时，先按项目 `list/routes`，检查匹配流程后复用；没有合适路径时录制首次可复用操作，并在最终断言通过后保存。一次性探索无需录制，未知效果不能盲目回放。已开始的 `ui_test` 仍通过自己的 act/check 完成步骤，保留范围、预算和证据。

这些说明在 MCP 连接初始化时下发；安装切换后要重连或重启宿主，现有连接缓存的说明不会自动刷新。工具服务提供指引，具体选择仍由宿主模型完成；后续可通过日志检查实际采用情况。日常日志用于按需观察，不替代受控的完整性能对比；不需要为每次检查重跑长测。
