## X1：完整 ArkTS 预检

真实 Studio 26.0.0.821、SDK 26.0.0.105，创建小工程后按顺序构建。计时包装实际服务调用，不替换 SDK 结果。每种条件只有一次样本，冷运行时不代表清空操作系统缓存。

| 条件 | 总耗时 ms | 同步 ms | 预检 ms | Hvigor ms | 预检占总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 新运行时，自动同步 | 4603.2 | 968.7 | 1014.5 | 2337.4 | 22.0% |
| 无变化，再次构建 | 2024.7 | 复用 | 1019.4 | 676.5 | 50.3% |
| 修改 ETS 源文件后构建 | 3691.9 | 复用 | 1025.1 | 2340.4 | 27.8% |
| 无变化，强制同步 | 2865.9 | 871.9 | 1024.3 | 690.5 | 35.7% |

总耗时还包含输入身份、回执和编排，因此不等于三列服务耗时之和。原始结果在 `preflight-cost/evidence.json`，脚本为 `measure-preflight.mjs`。

**判断：** 预检约一秒，是重复小工程构建的明显成本。现有 S1 已避免宿主额外重复检查，S3 已在源文件变化时复用有效同步回执。这两项有当前实现和测量依据。大工程的比例、不同 SDK 的收益未测量。

**缓存尚缺的合同：** 源文件及其导入闭包、实际依赖及链接目标、配置、SDK 与检查器版本、产品/模块和生成输入必须共同决定有效性；检查器私有缓存需要可持久化的完成回执、并发隔离及损坏回退。当前每次构造独立 checker 工程，不能直接把其中的缓存目录升级成跨任务缓存。只检查改动文件也不能证明整个工程仍然正确。

**后续启动条件：** 先在代表性大工程收集多轮冷/热样本，再验证检查器支持的增量接口；验证依赖变化、生成文件变化、跨模块错误与中断恢复不会遗漏诊断后，才引入可关闭、失效时退回完整检查的复用机制。本轮不以构建变快为由省略必要检查。

## X2：LangGraph

生产 `BoundedSqliteSaver`，每项 1000 次；不包含真实 SDK 或设备操作。原始数组保留在 `orchestration-final.json`。

| 测量 | 中位数 ms | P95 ms | 最大值 ms |
| --- | ---: | ---: | ---: |
| 无持久化单节点图 | 0.177 | 0.291 | 6.202 |
| 检查点写入、pending write 与读取 | 0.406 | 0.491 | 1.932 |
| 使用生产检查点的单节点图 | 1.197 | 1.562 | 5.779 |

**判断：** 当前热执行的编排成本远小于约一秒的 SDK 预检；单节点测量不能代表所有复杂链路。运行时按需导入工作流模块，纯连接目录读取不要求先启动图执行。

另用两种条件各五个新 Node 进程顺序测量模块导入，原始数据为 `module-cost.json`：

| 导入条件 | 中位耗时 ms | 导入后 RSS 中位数 MiB | 相应导入阶段 RSS 增量中位数 MiB |
| --- | ---: | ---: | ---: |
| 独立导入 LangGraph 及其传递依赖 | 106.4 | 181.6 | 141.5 |
| 先导入原生 Runtime 模块 | 85.0 | 121.9 | 81.9 |
| 接着按需导入 WorkflowEngine 模块 | 88.0 | 198.0 | 76.2 |

这是导入后的驻留内存快照，未强制 GC，未实例化完整服务或图，也没有逐依赖归因；不是保留堆、单个任务增量或泄漏测量。**加载成本明显存在**，不能用热调用耗时很小来忽略它。应继续保持按需加载，并把真实常驻 Worker 的冷启动、空闲 RSS 和峰值回落作为后续观察项；现有证据不足以证明重写状态机能稳定消除这些成本。

替换框架仍须自行维持持久化状态、检查点兼容、操作前后回执、中断核实、取消和恢复，不能只按“多数任务是顺序执行”删除这些语义。当前恢复测试和本地 MCP 进程重启验证已覆盖对应收益。维护重点放在限定工作流定义、共享执行步骤、收紧依赖升级合同，以及避免再引入第二套任务状态机。

**决策：** 保留 LangGraph。将启动和驻留内存单独观察，不能从热调用约一毫秒推断框架没有加载成本；只有代表性实测显示显著瓶颈，且替代方案通过同一恢复与历史任务合同，才讨论迁移。
