## 方法与边界

比较本轮实施前冻结工作区与最终候选，均运行实际 MCP stdio、Host/Worker、SQLite、公开工具 schema 和工作流。十类任务，两轮交替版本顺序，每个连接首次与重复两种样本，共 80/80 完成预定合同。每个版本每类只有四个样本，不作为统计显著性的证明。

SDK 构建、检查、同步与设备操作使用明确的测量适配器；工程创建使用实际 SDK 元数据和原生目录发布。测量保留实际编排、身份校验、持久化、图片传输、断言检查和恢复，但排除了真实编译、安装及设备时延。部署夹具包仅提供可解析的包元数据，不是可用于设备的密码学签名包。真实 SDK 检查另见最终验证报告。

“首次”指新 MCP 连接中首次计时的任务，已有构建部署等场景会先完成必要准备；“重复”指同连接第二次。它们不是操作系统缓存的冷/热测量。宿主采用固定脚本路由，没有模型推理时间。所有 JSON-RPC 请求/响应保留于各案例的 `wire.ndjson`，计数包含自动制品读取，字节按实际 UTF-8 紧凑 JSON 加换行计算，图像响应也计入。

普通构建、已有构建部署、错误修复与依赖锁变化路径在适配器条件下更慢；候选包含额外身份验证、摘要及引用工作，但未做逐函数归因，不能断言全部时延来自某一模块。构建运行与 UI 路径的调用和测量时延有所下降。结论是交互步骤减少，速度和总流量并非全面改善。

## 完成合同及局限

- 空目录创建：基线首次进入 needs_input，原因 PROJECT_EXISTS；脚本确认自有目录仍为空后用 rmdir 移除该空目录，再新建任务完成创建。四个样本均包含失败请求、轮询、一次宿主文件操作及重试。原 needs_input 记录保留在隔离状态中，没有把旧取消失败隐去。候选直接创建成功。
- 普通构建与构建运行：每轮一次预检、一次构建；构建运行一次安装和启动，启动合同为 process_only。候选重复构建可复用同步，保留完整预检。
- 已有构建部署：双方计时范围都不再构建；基线传包路径和应用参数，候选引用构建 ID 并核对来源；都一次安装和启动。
- 编译修复：预检夹具通过，构建适配器第一次确定失败；宿主修改自有源码后创建新任务，第二次成功。并不测量模型发现或修复真实错误的能力。
- UI：同样的控件断言和两份视觉要求；实际 MCP 图片字节交付后由脚本提交明确的夹具评价，最终 verified=true。不是用户界面的真实视觉质量验收。
- 日志调查：取消的 UI 任务只留下无可归属崩溃签名的日志。双方均完成分析并保持 diagnosisComplete=false；候选返回 insufficient_evidence，基线为 no_crash_signature。本案例检验证据不足分支，不证明真实故障根因定位。
- 依赖变化：修改自有锁文件字节而非实际下载依赖新版本，候选每次重新同步；这检验锁身份失效，不是依赖升级性能。
- 恢复：故意在启动边界丢失完成结果，实际重启 Worker 后恢复原任务；双方均保留安装 1 次、启动 1 次、核实 1 次，没有再次安装或启动。

脚本为证据根目录中的 `benchmark-mcp.mjs` 和 `benchmark-preload.mjs`。调试失败记录 comparison-1/2 保留；正式测量与最终回归的源码、编译产物、依赖锁和来源身份由 `final-identity.json` 核对一致。
