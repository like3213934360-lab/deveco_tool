## 真机测量

环境：macOS、Node.js，单台已连接 HarmonyOS 真机；不点击、不导航。12 轮轮换顺序，每轮比较四种查询方式，当前树稳定为 569 节点。合计 120 次测量调用、2 次预热，74 次设备抓取。数字为本地工具实现耗时，排除 Codex 客户端和 MCP 编解码开销。

| 查询方式 | P50 | P95 |
| --- | ---: | ---: |
| 四次独立实时查询 | 5937 ms | 6070 ms |
| 一次批量查询四种控件 | 1484 ms | 1588 ms |
| 对已有快照查询四次 | 7.73 ms | 17.22 ms |
| 截图并抓树、批量查询 | 1597 ms | 1751 ms |

批量查询减少约 75% 延迟，也避免四次采样间界面变化。快照复用的毫秒级结果不代表实时抓取速度。

批量查询分段中位数：HDC 设备解析 16.4 ms、锁等待 0.17 ms、设备 dumpLayout 1325 ms、传输 47.0 ms、设备清理 90.2 ms、本地树解析 0.80 ms。宿主进程 CPU 中位数 8.5 ms。各段部分重叠，不应求和。

快照实际文件数达到上限后保持 64。基准进程 GC 后堆从 5.12 MiB 到 6.01 MiB，RSS 从 61.1 MiB 到 93.8 MiB；基准本身持续保存测量记录，不能把这段增长直接认作泄漏或宣称不存在长期泄漏。事件循环采样分辨率 20 ms，P95 21.1 ms、最大 43.5 ms，包含调度和 GC。

修复前额外测量的 592 节点页面：单次查询 1.47–1.60 秒、截图抓树 1.50–1.75 秒。前后页面节点数不同，因此加速结论使用上述同一轮组内四次查询与批量查询对比，不把两次页面直接当成严格 A/B。

## 底层优化判断

需要一项针对性的底层环境优化，已实现：MCP SDK 的最小环境没有 TMPDIR 时，同一 HDC 二进制执行 list targets 约 1326 ms；仅补 TMPDIR 后为 16.6 ms。逐一补 DEVECO_HOME、LANG、LC_ALL、MallocNanoZone 均未改善。修复前最小环境下两次 ui_find 分别 5.35/5.56 秒，截图抓树一次 6.66 秒，且 500 ms 清理会超时。这是额外真机验证发现的问题，不追溯断言上午日志已出现。

修复后重新启动最小环境 stdio MCP 服务，5 次批量查询分别为 1481、1478、1508、1386、1386 ms，设备枚举恢复到 16–23 ms；截图抓树 1586 ms，复用同一快照 0.86 ms，内联返回 1 张截图且临时文件确认删除。真实 Toggle 状态通过查询返回；未对设备发送测试点击。

当前约 89% 的批量查询时间在设备 dumpLayout。本地解析不足 1 ms、CPU 约 8.5 ms，缺乏重写解析器、增加 worker、替换原生传输或改动图片编解码的收益依据。现有截图与抓树已并行。优先减少设备抓取次数已获得约 4 倍查询吞吐改善。

清理约 90 ms，改成异步可能与固定设备路径的下一次写入竞争，不为小幅收益改变清理时序。若未来产品需要单次实时抓树明显低于 1 秒，应单独验证设备侧持久 UI 自动化服务、事件订阅或差分树，并测试不同系统版本；当前数据不足以证明这些方案可靠。
